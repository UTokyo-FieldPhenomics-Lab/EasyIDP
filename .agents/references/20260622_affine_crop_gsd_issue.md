# Affine GeoTIFF Crop GSD Issue

## Summary

`easyidp.geotiff.back2raw2geotiff(..., use_affine=True)` can generate rotated GeoTIFF crops whose x/y pixel sizes differ substantially from the raw image projected ground sampling distance (GSD). The GeoTIFF is geographically placed correctly in QGIS because the affine transform is valid, but the output image can be visibly resampled to a poorer resolution along one axis.

This appears to be an EasyIDP-side implementation issue rather than a user-script issue. The current implementation mixes axis-aligned bounding-box dimensions with rotated rectangle dimensions when estimating pixel sizes.

## Root Cause Evidence

The relevant code path is in `src/easyidp/geotiff.py`.

`back2raw2geotiff(..., use_affine=True)` calls `_process_single_image_task()`, which calls:

```python
gtiff = one_raw_roi2geotiff(...)
if use_affine:
    gtiff = gtiff.convert_to_affine()
```

`one_raw_roi2geotiff()` estimates scale using axis-aligned bounding boxes:

```python
geo_width = roi_geo_2d[:, 0].max() - roi_geo_2d[:, 0].min()
geo_height = roi_geo_2d[:, 1].max() - roi_geo_2d[:, 1].min()
px_width = roi_raw_px[:, 0].max() - roi_raw_px[:, 0].min()
px_height = roi_raw_px[:, 1].max() - roi_raw_px[:, 1].min()

scale_x = geo_width / px_width if px_width > 0 else 1.0
scale_y = geo_height / px_height if px_height > 0 else 1.0
```

For rotated rectangles, the axis-aligned bbox does not represent the ROI local width/height. In the example:

```text
geo bbox width / raw bbox width  = 0.760474 / 227.25 ~= 0.00334685
geo bbox height / raw bbox height = 0.997825 / 154.90 ~= 0.00644162
```

These are the exact pixel sizes stored in the final affine output.

`convert_to_affine()` then uses these already-skewed `pixel_size_x` and `pixel_size_y` values to compute rotated rectangle dimensions:

```python
pixel_size_x = abs(old_transform.a)
pixel_size_y = abs(old_transform.e)

pixel_width = rect_width / pixel_size_x
pixel_height = rect_height / pixel_size_y
```

Because `rect_width=0.9m` and `rect_height=0.6m`, the final dimensions become:

```text
0.9 / 0.00334685 ~= 269 px
0.6 / 0.00644162 ~= 94 px
```

This explains the observed `269 x 94` output.

## Why This Is Not Merely a Feature

Affine GeoTIFF storage may legitimately encode rotation in the transform. However, it should not introduce a large mismatch between x/y pixel vector lengths unless that anisotropy reflects the source data or an explicit user request.

In this case:

```text
DOM GSD:              0.00436 m/px x 0.00436 m/px
raw edge-derived GSD: 0.00404 m/px x 0.00404 m/px
output affine GSD:    0.00335 m/px x 0.00644 m/px
```

The output anisotropy comes from implementation details of bbox-based scale estimation, not from the raw image geometry or DOM metadata.

## Important Distinction

This is not a simple width/height swap bug.

The root problem is coordinate-frame mixing:

- `one_raw_roi2geotiff()` computes `scale_x` / `scale_y` from axis-aligned bbox axes.
- `convert_to_affine()` interprets those scales along the rotated ROI local column/row axes.

For non-rotated rectangles these frames are the same. For rotated rectangles they are not.

## Expected Behavior

When `use_affine=True` for a rectangular ROI, EasyIDP should generate a rotated GeoTIFF whose pixel spacing is consistent with the source image projected scale or a requested target GSD.

For the example above, an acceptable output should be close to one of:

```text
Raw projection GSD preserving:
  width ~= 223 px, height ~= 149 px, pixel size ~= 0.00404 m/px

DOM GSD preserving, if target GSD is DOM-driven:
  width ~= 206 px, height ~= 138 px, pixel size ~= 0.00436 m/px
```

The final affine transform should still place the crop correctly in QGIS.

## Suggested Fix Direction

### Recommended: direct raw-to-affine one-pass warp

The final goal is not only to write a GeoTIFF with valid affine rotation. The goal is to preserve the source raw RGB image's projected resolution as much as possible, while placing the crop correctly in the target CRS.

The current `use_affine=True` path does two resampling steps:

```text
raw RGB image
  -> one_raw_roi2geotiff(): projective warp into an axis-aligned GeoTIFF
  -> convert_to_affine(): map_coordinates(order=1) into a rotated affine GeoTIFF
```

This is undesirable even after fixing the GSD math, because the RGB data is interpolated twice. The corrected `back2raw2geotiff(..., use_affine=True)` path should instead do one direct warp:

```text
raw RGB image + raw ROI pixel coordinates + geo ROI coordinates
  -> direct projective warp into the final rotated affine GeoTIFF grid
```

Keep `one_raw_roi2geotiff()` unchanged for the standard non-affine path. Add a separate internal helper for the affine path, for example `_one_raw_roi2affine_geotiff()`, and call it from `_process_single_image_task()` only when `use_affine=True` and the ROI is a valid rectangle. If rectangle parsing fails, fall back to the existing standard path.

### One-pass affine algorithm

1. Remove the duplicated closure vertex from `roi_geo_coords` and `roi_raw_px_coords`.
2. Parse the geo ROI rectangle with the existing order-independent rectangle logic used by `GeoTiff._get_rectangle_affine_info()`:
   - `origin`: final affine top-left corner in geo coordinates.
   - `col_vec`: unit vector along output image columns.
   - `row_vec`: unit vector along output image rows.
   - `rect_width`: geo width along `col_vec`.
   - `rect_height`: geo height along `row_vec`.
3. Estimate source projected GSD from corresponding geo/raw polygon edges:

```python
geo_edges = np.roll(roi_geo_2d, -1, axis=0) - roi_geo_2d
raw_edges = np.roll(roi_raw_px, -1, axis=0) - roi_raw_px

geo_lengths = np.linalg.norm(geo_edges, axis=1)
raw_lengths = np.linalg.norm(raw_edges, axis=1)

valid = raw_lengths > 1e-10
target_gsd = float(np.median(geo_lengths[valid] / raw_lengths[valid]))
```

4. Use the same `target_gsd` for both output axes:

```python
out_width = int(np.ceil(rect_width / target_gsd))
out_height = int(np.ceil(rect_height / target_gsd))
```

5. Convert geo ROI vertices into final affine image pixel coordinates:

```python
local_geo = roi_geo_2d - origin
dst_px = np.column_stack([
    local_geo @ col_vec / target_gsd,
    local_geo @ row_vec / target_gsd,
])
```

6. Estimate a single projective transform from raw image pixels to the final affine pixel grid:

```python
pt = ProjectiveTransform()
pt.estimate(src=roi_raw_px, dst=dst_px)
```

7. Crop the raw image around the raw ROI with the existing 10% buffer, subtract the crop offset from `roi_raw_px`, and estimate the projective transform using local raw pixels. Then perform one RGB resampling step:

```python
warped_img = warp(
    cropped_img,
    pt.inverse,
    output_shape=(out_height, out_width, cropped_img.shape[2]),
    preserve_range=True,
    cval=nodata,
).astype(cropped_img.dtype)
```

8. Build the final affine transform directly from the same geo vectors and `target_gsd`:

```python
transform = Affine(
    target_gsd * col_vec[0],
    target_gsd * row_vec[0],
    origin[0],
    target_gsd * col_vec[1],
    target_gsd * row_vec[1],
    origin[1],
)
```

9. Return a `GeoTiff` whose `imarray` is already the final rotated crop, whose profile contains the affine transform, and whose `_use_affine` is `True`.

### Interpolation and resolution notes

- This path still resamples once. A projective mapping from raw camera pixels into a rectangular output grid cannot generally be stored without any resampling.
- The important improvement is that it avoids the second `convert_to_affine()` interpolation step.
- The output pixel vector lengths should both match the raw edge-derived projected GSD, so EasyIDP no longer intentionally downsamples one axis.
- `skimage.transform.warp()` should use a single, explicit interpolation setting. For RGB photographs, use linear interpolation (`order=1`) to match the current behavior and avoid nearest-neighbor stair stepping. If strict pixel-value preservation is needed for categorical data, that should be a separate option, not the RGB default.

### Optional later enhancement: explicit `target_gsd`

Add an optional parameter in a separate change if downstream users need DOM-aligned outputs:

```python
back2raw2geotiff(..., use_affine=True, target_gsd=None)
```

Behavior:

- `target_gsd=None`: estimate from raw projected ROI edge lengths.
- `target_gsd=float`: use explicit meter-per-pixel value.

This is useful, but not required to fix the current raw-resolution-preserving bug.

### Backward compatibility boundary

Keep the non-affine path unchanged. The standard bbox-based `one_raw_roi2geotiff()` output may be relied on by existing users, so the first fix should only change `back2raw2geotiff(..., use_affine=True)` for valid rectangular ROIs.

## Downstream Workaround

Until EasyIDP is fixed, downstream ML dataset generation should avoid relying on `use_affine=True` when fixed or source-consistent GSD is required. A downstream script can instead implement a custom warp using a chosen target GSD, usually either:

- the raw projected edge-derived GSD, or
- the matching DOM GSD.

For the R6 dataset, DOM GSD is about `0.0043638557 m/px`; raw projected GSD for the investigated ROI is about `0.004043 m/px`.
